# A recipe reaches the server only when sent, in one request; no outbox holds recipes

**Status:** accepted — supersedes [20260927-server-authoritative-sync-with-outbox.md](20260927-server-authoritative-sync-with-outbox.md), and the words "the synchronisation outbox and media uploads" of [20260927-android-client-stack.md](20260927-android-client-stack.md), which otherwise stands
**Date:** 2026-09-28 · amended 2026-09-29 (spec/ @ 952398f, SD-041) · amended 2026-10-01 (spec/ @ e70b62c, SD-044, SD-045: a fork already made is checked before sameness; a lost recipe and a sending with no revision) · amended 2026-10-02 (spec/ @ 86164a9, FLOW-067: a sending after an unanswered one is made from what it stored)
**Requirements:** FLOW-002, FLOW-003, FLOW-004, FLOW-005, FLOW-006, FLOW-007, FLOW-008, FLOW-052, FLOW-059, FLOW-066, FLOW-067, ST-009, ACT-002, DOM-005, MEDIA-010

**Context:** A recipe is written on the device by anyone and reaches the server only when its owner sends it (FLOW-002, FLOW-059). A sending that fails queues nothing, and the server holds the whole sending or nothing of it (FLOW-059 (8)); a sending whose answer was lost is settled by sending again (FLOW-059 (9), FLOW-066). Each recipe shows one of three marks: never sent, sent with every change, sent with changes not sent (FLOW-005). A recipe's identity is given when it is created on the device and kept when it is sent, so that a fork can name a parent the server does not hold (FLOW-007, the domain model's `recipe_id`). Divergence between devices is found at sending and becomes a fork (FLOW-008). Favourites and blocks keep reaching the server by themselves (FLOW-052).

**Decision:**
- A recipe's identity is a UUID minted on the device when the recipe is created. The server accepts it as the recipe's primary key on the first sending and never mints one.
- Sending is one HTTP request per recipe: a multipart body holding the recipe document and every media item it carries that the server does not hold yet. The server writes the media to object storage under staging keys, then writes the recipe, its revision and its media references in one database transaction; on any failure it deletes what it staged and answers with the failure. The device changes nothing until the answer says the recipe was stored.
- Every sent recipe carries a server revision. The device keeps, per recipe, the revision its copy was made from and a digest of the content it last sent. A sending names that revision; a sending that names none is taken as made from the recipe's first revision (FLOW-059 (14)), and one for a recipe the server no longer holds creates it again as on a first sending (FLOW-059 (13)). The server checks first whether the same sending — the same content, made from the same revision — already made a fork; if so it answers with that fork and makes no second one, whatever its own content has become since (FLOW-066 (4), FLOW-008 (7)). For that it remembers which sending made each fork. Only otherwise: if the sent content — every field and every media item — is the same as the content the server holds, the server writes nothing, makes no fork, and answers that the recipe is sent, with the state it holds (FLOW-066). Otherwise, if the server's revision differs from the one named, above or below it, or its state changed alone, the server keeps its version and stores the sent one as a `private` fork owned by the same account, and says so in the answer (FLOW-008).
- Every sending carries an identity the device mints for it (a UUID), and the identities of the device's earlier sendings of that recipe that went unanswered since it last learned what the server holds of it, oldest first. The device keeps those identities, per recipe in the recipe's book database, until an answer reaches it. The server records, for each sending it stores, its identity and what it left: the revision it wrote, or the fork it created. A sending that names unanswered identities is taken as made from what the latest of them that the server stored left — that revision, or, when it is a fork, the fork itself, against which the sending is then answered (replaced if unchanged since, forked by FLOW-008 if another device changed it); identities the server never stored are passed over, and if none was stored the sending is made from the revision it names (FLOW-067, FLOW-008 (8)). The check of a fork already made (FLOW-066 (4)) and of sameness (FLOW-066) then apply as for any other sending, against that base. A sending that names no revision and no stored unanswered identity is still taken as made from the first revision (FLOW-059 (14)), the case FLOW-067 (7) names.
- The mark of FLOW-005 is computed on the device: no revision means never sent; a revision with a content digest equal to the last sent digest, and no media added since, means sent; otherwise, changes not sent.
- The device holds no queue of recipe operations. WorkManager carries only what FLOW-052 sends by itself — favourites and blocked authors — as a small outbox of those operations.
- Acts that FLOW-003 refuses are never written anywhere to be retried.

**Consequences:**
- The server keeps one small record per stored sending (its identity, the recipe and what it left); records are kept with the recipe and deleted with it, so nothing of a deleted recipe remains (ST-010). The device keeps, per recipe, the identities of its unanswered sendings, the cost FLOW-067 states.
- No merge logic exists anywhere, as before.
- The largest request the server receives is one recipe with its media, tens of megabytes at most; the server's request size limit is set from the media limits of MEDIA-001 to MEDIA-009.
- Staged objects left by a crash between staging and commit are orphans; the media sweep of MEDIA-012 deletes objects no recipe holds, which covers them.
- A recipe's identity is visible to whoever holds a file of it (FLOW-063) and is not secret; nothing grants access by it, because the server checks ownership and visibility on every request.

- Amended 2026-09-29: sameness is decided over the whole content, so the server keeps a digest of each stored content and of each sending that made a fork; the device keeps the digest it last sent, as above. Before wave 5 the content has no media and the digest covers the document alone.

**Alternatives considered:**
- *The device sends the content digest of its unanswered sending instead of an identity.* Rejected: two sendings of the same content from different devices would be one to the server, and FLOW-067 (2) needs to tell this device's sending from another's.
- *Keep the outbox and drain it when the owner presses send.* Rejected: FLOW-059 (8) requires a failed sending to queue nothing; an outbox is a queue.
- *Send the text first and the media in later requests.* Rejected: a failure between them leaves text without media on the server, which FLOW-059 (8) forbids.
- *Fork every sending made from an older revision, even with the same content* (the rule before 2026-09-29). Rejected by spec/ @ 952398f (FLOW-066): an owner whose answer was lost would get a fork identical to its parent on every retry.
- *Server-minted identities, assigned at the first sending.* Rejected: a fork of an unsent recipe must name its parent before the parent is sent (FLOW-007), and a file must be recognised when imported twice (FLOW-064).
