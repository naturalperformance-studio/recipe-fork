**Failed check:** C3 — on the trigger the task now carries, the behaviour cannot be compared with the requirement, because the requirement can be read more than one way.
The entry now carries two FLOW-034 criteria that bound one choice from both sides:
- (5) "Given a switch between the views, when the reader leaves the section and returns within the same session, then the view they were in is still in force, as CAT-001 keeps a chosen ordering."
- (6) "Given a session in which the reader has not chosen a view, when they open the section, then it opens on the view of marked recipes, whatever the account holds."

So a chosen view must be kept for the rest of a session and must be gone when the next session starts. `spec/` defines "session" nowhere: not in `spec/10-glossary/`, not in FLOW-034, and not in CAT-001 (6) or FLOW-033, which use the same words. The earlier verdicts recorded this as harmless (unknown (1) of the first, unknown (3) of the second). That held while (5) was the only criterion carried, because an implementation that keeps the view forever satisfies (5) under every reading. With (6) in the entry, where a session ends decides what the reader sees.

The spec treats the three events that could end a session as different events. FLOW-012 and AUTH-024 separate them:
- leaving the application and returning while its process is alive;
- the operating system ending the process while the application is away;
- the reader closing the application.

FLOW-017 contrasts "a later session" with "stays in the application", which suggests a session is one run of the application. It does not say whether a run that the operating system ended and Android restored is the same run. Take a reader who chose the own-recipes view and returns after the operating system ended the process, or who closes and reopens the application. One reading of FLOW-034 requires the section to open on the marked view. Another requires the own-recipes view to still be in force. An implementation that keeps the choice in memory, one that keeps it in restorable state, and one that writes it to the device each meet one reading and fail another. The developer would choose among them, and gate 2 could not tell a right choice from a wrong one (TEAM-008).

Reading under which the entry would pass: "session" in its ordinary sense, one run of the application, as FLOW-017 suggests. That reading does not hold here. It leaves the process-ended case open, and the specification elsewhere treats that case as a product decision. It asked the user separately for FLOW-012 (SD-026) and for AUTH-024 (in the re-check of SD-009). Choosing a reading would be making that decision.

The task cannot correct this, because C5 requires it to copy (5) and (6) as written. Class: ambiguity. No replacement is stated (PO-006). Route: the user runs `/req-forge` on SD-028. The task returns to gate 1 when FLOW-034 changes. `blocked-by-spec` is not a return (TL-011).
