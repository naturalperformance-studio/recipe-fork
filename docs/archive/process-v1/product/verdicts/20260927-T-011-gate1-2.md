**Failed check:** C3 — the trigger of a carried criterion is defined by a requirement the task neither names nor precedes, so the trigger the task hands a developer is wider than the one the requirement states.
The entry carries FLOW-023 (3) word for word: "Given the ingredient field, when what the author typed matches a parent, then its leaves are offered before it (FLOW-057), …". What "matches" means is stated in one place only, FLOW-057: "every dictionary entry whose label, in either interface language, holds for each typed word a word that begins with it, ignoring letter case and treating `ё` and `е` as one letter", with the leaves of an offered parent placed "immediately before that parent". The spec ADR that wrote FLOW-057 rejects any other rule by name, and because of this very criterion: "*Each entry matched on its own label only.* Rejected: FLOW-023's leaves-first rule would almost never fire." The same rule is what decides the Then of FLOW-023 (2) ("dictionary entries are offered") and of FLOW-001 (4) ("offers the same entries it offers with a connection"). All three describe which entries the field offers for what the author types, and FLOW-057 is the requirement that states it.
T-011 does not name FLOW-057. The requirement is carried by T-031, which depends on T-011. The developer agent receives only the requirements its task names (TL-008), so it would build FLOW-023 (2) and (3) with no rule for "matches". The choice of rule would then be made in code, although it is the product decision that SD-008 item 1 and SD-006 took to `/req-forge` and that FLOW-057 now records. Every rule would satisfy the three criteria as this task carries them. A test that types `курица` under a seeded dictionary passes whether matching is by exact label, by prefix of the label, or by FLOW-057, and the offer for `кур`, `Кур` or `chick` would stay whatever the developer chose. The T-031 note states that T-031 builds the folding stage. So the offer T-011 ships to `develop` is, by design, not the one FLOW-057 describes, and it is judged at gate 2 against a trigger this task leaves undefined.
The reading under which the task would pass: FLOW-023 (3)'s "(FLOW-057)" is a cross-reference like "(DOM-010)" in criterion 2, and a provisional offer is acceptable until T-031 lands. That reading does not hold. Every other requirement the entry's criteria cite in parentheses (DOM-010, DOM-002, FLOW-001, FLOW-023, DOM-009) is named in the entry and reaches the developer. FLOW-057 is the only one that does not. It is also the one that defines the criterion's trigger rather than restating something alongside it, and gate 2 could not decide whether a test's input "matches a parent" without it.
Without stating how the backlog is sliced: the task passes C3 once the rule that defines "matches" reaches the task that carries FLOW-023 (2), FLOW-023 (3) and FLOW-001 (4), and is built no later than they are. The task then returns to gate 1.
