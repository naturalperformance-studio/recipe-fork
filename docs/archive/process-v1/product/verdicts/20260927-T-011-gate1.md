**Failed check:** C3 — the behaviour the requirements state is not determinate on three of the triggers this task carries, so the task cannot be compared with them.
T-011 builds the three fields of an ingredient row in the editor. (1) FLOW-023 (3) orders leaves before a parent "when both a leaf and its parent could match what the author typed"; read as label matching, `крылышки` and `курица` rarely match the same text and the criterion almost never fires; read as matching through the family, typing `курица` offers its leaves first, which is what the criterion's own purpose ("a qualifier is a last resort and not a substitute for picking the right entry") and OQ-020 describe. The two are different lists. (2) The unit field must offer a set of units, each mapped to its unit type (FLOW-023 (7)); the domain model's unit-type table labels its units "Examples", the glossary lists `household` (teaspoon, tablespoon, cup) and `taste_measured` (a pinch) in parentheses, L10N-008 requires every unit to be "one of those DOM-002 defines" while DOM-002 defines none, and the only `piece` unit named anywhere is `шт`. Whoever writes the field decides which units an author can write. (3) FLOW-023 (8), on picking "to taste" in the unit field, withdraws "the quantity field"; DOM-002 (1), for the same `taste_unmeasured` ingredient, has "the editor offers no field for either" quantity or unit. A row that keeps its unit field showing "to taste" fails DOM-002 (1) as written; a row that drops it has no stated way back and is no longer the three fields of FLOW-023 (1). SD-006 item 1 (the text-matching rule) also underlies FLOW-023 (2), FLOW-023 (3) and FLOW-001 (4). Classes: ambiguity (1), omission (2), inconsistency (3). No replacement is stated (PO-006). Route: the user runs `/req-forge` on SD-008 and SD-006; the task returns to gate 1 when those requirements change. This is not a return (TL-011).
