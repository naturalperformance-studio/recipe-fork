**Failed check:** C3. On a trigger the task's own criterion names, `spec/` does not say what happens. The owner sends again a recipe the server no longer holds.
T-040 carries FLOW-059 (4): "Given a sent recipe edited on the device, when it is sent again, then the server's copy is replaced by the device's version, unless FLOW-008 finds the two diverged." It also builds the statement's first sending ("creating it there in `private` on its first sending"). The server must answer every sending, and one kind of sending falls between the two:
- *After a restore.* QUAL-008 loses "at most one hour of accepted work", and QUAL-008 (3) says "nothing accepted after the copy began is present". A recipe first sent inside that hour is held on the device with a revision the server gave it, and the server no longer holds the recipe. The owner edits it and sends it.
- *After deletion on another device.* ST-010 (2): a recipe in `private` deleted by its owner "is gone from the server and from every device the account holds". Device B still holds it with a revision until it learns of the deletion. If the owner edits it there and sends, the server does not hold it.

What `spec/` says, read and not chosen:
- FLOW-059's statement creates the recipe "on its first sending" and replaces "the server's copy on a later one". This sending is not the recipe's first, and the server holds no copy to replace. FLOW-059 (4)'s *Then* ("the server's copy is replaced") has no object.
- FLOW-008 needs "the server's version" to keep as the recipe and to fork from. There is none.
- FLOW-059's statement says that when the owner chooses to send, "the system shall send that recipe". Refusing the sending every time leaves the recipe permanently unsendable, and by FLOW-006, permanently unsubmittable. Creating it again brings a recipe the owner deleted back to the server, and ST-010 (2) says it is gone from the server. RET-004 (4) accepts that a restore undoes deletions, but it says nothing about a device sending into the restored store.
- The server cannot tell the two routes apart: ST-010 destroys the recipe and keeps no record of it.

The entry's note refuses every revision "the server never issued", which reads as a refusal here. Refusal, creation again, and a distinct answer for each route are three products. Whoever builds the task would choose one, and gate 2 could not tell a right outcome from a wrong one (TEAM-008). Rejecting the entry would not help: a corrected entry faces the same question, and choosing the answer is the product decision (PO-006). Class: omission. Route: the user runs `/req-forge` on SD-045. Stopped: T-040.

Counterfactual: the entry would pass C3 on this point if `spec/` said what a sending gets when it names a revision for a recipe the server does not hold. The gate looked in FLOW-059, FLOW-008, FLOW-066, FLOW-003, ST-010, FLOW-053, QUAL-008, RET-004, the ADR `spec/decisions/20260921-an-hourly-snapshot-is-the-whole-safety-net.md` (it does not mention a device, a sending or a revision), and the binding sending ADR, and found none. The binding ADR says the server "accepts [the identity] as the recipe's primary key on the first sending" and is silent on this case.
