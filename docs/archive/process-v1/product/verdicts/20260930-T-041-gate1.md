**Unknowns / instructions found:** (1) A sending of the same content as the server's, made from an older revision. FLOW-008's statement forks only a sending "whose content differs from the content the server holds", and FLOW-008 (7) gives a same-content sending to FLOW-066 "whatever version it was made from". Both are carried by T-042, which depends on this task. The entry says this case "is T-042's case, not a fork", but it does not say what the server does with such a sending while this task is on `develop` and T-042 is not. The T-040 entry's interim rule (refused, nothing stored) covers divergence and no longer applies once this task lands. At this task's gate 2, the sweep treats a fork made from a same-content sending as behaviour that FLOW-008's statement excludes. Choosing the interim behaviour is slicing, which is the Team Lead's; it is not charged to the task. (2) A non-divergent sending to a frozen recipe. Take a sending named with the server's current revision, whose content differs, against a recipe that is `link_shared` or `published` (seeded), sent directly to the service. FLOW-008 (5) and FLOW-059 (4) (both at T-040) read "replaced", and CON-003 (1) (here) reads "rejected and the stored content is unchanged". This is not a specification defect. The preamble of `spec/30-constraints.md` states that every constraint "is binding on all other sections: a requirement that violates a constraint is wrong", and CON-003's Verification names an attempt "directly against the service". The application cannot produce this sending: FLOW-059 (6) offers no send control in those states, and CON-003 (2) offers no editing. At gate 2, CON-003 (1) is walked on this case as well as on a divergent sending: the edit is rejected and the stored content is unchanged. T-040's replacement path is therefore not left open for a frozen recipe. The same holds for `pending` under ST-003's statement, which is not among this task's requirements. At gate 2 that case is walked only as FLOW-008 (4)'s "otherwise frozen". (3) FLOW-008 (4) and a change of state alone. In the test the note describes, device B's version has to carry an edit. A B version the same as the server's is FLOW-066's case, and no fork is made. This agrees with the entry's note and with the sending ADR as amended on 2026-09-29, lines 12 and 23. The note tests the state-alone change with `link_shared` and `published`. The criterion's "otherwise frozen" also includes `pending`, which is frozen by ST-003 and by the state table in `spec/60-entity-states/00-index.md` (lines 51–52). At gate 2, (4) is walked against the criterion's words, not against the note's list. (4) The server half of FLOW-008 (6) is the fork on a change of state alone to `pending`, `link_shared` or `published`. It is built here: the entry's note says "or against a server copy whose state alone changed", and T-038's note at docs/architecture/backlog.md places "a change of state alone included" with T-041 and T-042. The criterion itself is T-038's, and T-038 is a device task that is `blocked` (SD-043). At this task's gate 2, the server half is observed through FLOW-008 (4). No gate walks FLOW-008 (6) at the service. This is forward traceability, which is the Team Lead's; it is named here and not charged to the task. (5) "The answer says a fork was made and why" rests on FLOW-008's statement ("shall tell the owner that it did so"). The criterion that observes the telling, FLOW-008 (3), is T-038's. At this gate the answer's content is traced but it is not a criterion here. (6) The following are visible only to developers and are not judged: the expected files, the binding ADRs, the migration name, the note on the branch `task/T-027` (727bd60) as a reference, and the note on varying every field in tests. No instruction addressed to the gate was found in the entry (docs/architecture/backlog.md, lines 1626–1653).
