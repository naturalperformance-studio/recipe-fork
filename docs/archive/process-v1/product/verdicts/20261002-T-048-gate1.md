**Spec defect written:** SD-046 in docs/product/spec-defects.md

**Failed check:** C3. The requirement this task builds gives one reachable sending two different outcomes, and the two disagree on what a user can see. The trigger is an unanswered sending that the server answered under FLOW-066 by writing nothing.

The sequence, with two devices on one account:
1. The server holds the recipe at r1 with content Y, and both devices hold r1.
2. Device A sends edit X. The server writes r2 = X.
3. Device B, still made from r1, makes the same edit X and sends it (sending S1). Its content is the same as the server's, so FLOW-066 (2) answers it: "the server's copy is unchanged, no fork is created". The answer to S1 is lost.
4. Device B still holds r1, keeps its mark (FLOW-059 (9)), and keeps S1 as unanswered (FLOW-067, Cost).
5. The owner edits the recipe on device B to X′ and sends it (sending S2).

FLOW-067's statement takes S2 as made from "what the latest of those unanswered sendings that the server stored left there — the revision it wrote to the recipe, or the fork it created under FLOW-008". S1 wrote no revision and created no fork. Two readings follow:
- *Reading 1: S1 is not a sending the server stored.* It left nothing there, so FLOW-067 (3) applies: "the sending is made from the revision the device held before that sending, as if it had never been made". S2 is made from r1. The server is at r2, and X′ differs from X. FLOW-008's statement and (2) then make device B's version a `private` fork, and the owner is told. FLOW-008 (8) does not apply, because r2 was written by device A, not by this device's own sending.
- *Reading 2: S1 is a sending the server stored.* The ADR of 2026-09-29 says a sending "is stored whole or not at all", and S1 was received whole and answered. What it left there is r2, the revision the server held and answered with. S2 is made from r2, so FLOW-059 (4) replaces the server's copy, and no fork or notice follows. FLOW-067's Source supports this reading: "The device's edit was made on top of what it sent, so what it was made from is what that sending stored". So does the rejected alternative in its ADR: "the owner gets a copy of their own recipe and a notice about a divergence that never happened". Device B's X′ was made on top of content identical to r2.

What a user sees differs. Under reading 1, a fork exists and the owner is notified of it. Under reading 2, the recipe is replaced with no fork. FLOW-066 (3) gives the same split: there, S1 is answered `pending` with nothing written, and S2 is made either from r1 under a state that has changed since, or from the server's version as S1 left it. To build the server, the developer has to decide whether S1 leaves a record. Gate 2 would then have no way to call the result right or wrong (TEAM-008).

This is not `rejected`. The entry describes the requirements neither more narrowly nor more widely, and C5 obliges it to copy FLOW-067 as it stands. A returned entry would come back identical and spend one of its two returns (TL-011). The task would pass if "stored" meant only a sending that wrote a revision or created a fork, or if it meant every sending received whole. No word in `spec/` says which, and choosing between them is the product decision. Class: ambiguity. The route is `/req-forge`.
