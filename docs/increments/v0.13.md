# v0.13 — A short silent clip on a step
**Status:** active
**Planned:** 2026-10-03 · **Shipped:** —

Planned by the lead under the user's standing instruction (v0.9 decision log): v0.12's build was delivered at 11:14 and no answer came within 20 minutes. From `serverless-roadmap.md`, increment D.

## Goal
A step can show a short silent clip instead of a photo — shot with the phone's camera or picked from the gallery, made small and soundless on the phone — it loops on the card, travels in a recipe file and a fork, and media the device does not need can be cleared after a warning.

## What exists at the start
On `develop` @ f496117 (v0.12 at demo). The model already knows `MediaKind.VIDEO`; the recipe file (format 1) already carries a video (golden `media/m-2.mp4`, 6 MB cap, `ftyp` check) and import and fork keep it. But the card and the editor show photos only (`Recipe.stepPhoto` filters PHOTO), a missing media file is skipped silently, and `RecipeEditor.setStepPhoto` removes only a PHOTO — a photo added to a step holding an imported video leaves two items, which our own importer then refuses. No video can be attached, converted or played; Media3 is not a dependency. Orphaned files are already swept (`MediaSweep`).

## Demo scenarios
1. On a step, "Record a clip" opens the phone's camera, limited to 15 s; a notice says the clip was converted and its sound removed; on the card it loops silently, a 56 dp button pauses it, TalkBack calls it the author's video.
2. Pick a 40 s clip from the gallery: refused at once, the message names 15 seconds. Pick a large ~12 s clip: it attaches, small enough (≤ 1280 px, ≤ 6 MB).
3. Replace a step's photo with a clip, then the clip with a photo: the step holds one item each time. Fork your own recipe with a clip and delete the original: the fork's clip still plays.
4. Export a recipe with a clip, delete it, import the file: the clip plays on the card.
5. Import a found recipe with photos, then "Clear saved media" in the book's menu: a warning says it cannot be fetched again; Cancel changes nothing; Confirm leaves the found recipe saying its media is unavailable while your own drafts keep theirs.

## Out of scope
- Converting an animated image (GIF/WebP) to a video (MEDIA-004 last sentence): it stays a still photo, as today. Logged in later.md.
- Server-only parts: the storage allowance (MEDIA-010/011), upload, fetching media again (FLOW-060 (1), (3)), the FLOW-011 setting.

**Criteria:**

**Notes:** Passed review with the mutation check on the first round. `setStepMedia` replaces an item of either kind (the photo path goes through it, fixing the two-items bug); `VideoLimits` in core; the import reads a clip's length off the main thread and refuses over 15 s ("longer than 15 seconds") or an unreadable length (the damaged-file message), deleting everything it wrote. Nits left: the too-long test is repeated outside core; no test with a throwing duration reader.

### T-115 — A clip is made short, small and silent
**Status:** done
**Serves:** scenarios 1, 2 · **Core:** no · **Depends on:** T-114
**Expected files:** `gradle/libs.versions.toml`, `app/build.gradle.kts`, `app/proguard-*.pro`; new `app/.../media/Video*.kt`; `app/src/androidTest/.../VideoConversionTest.kt`; JVM tests for what can run there.
**Criteria:**
- MEDIA-004: a clip is converted on the device to ≤ 1280 px on its longer edge (never enlarged), ≤ 6 MB, with no audio track; Media3 Transformer behind an interface (the ADR's choice).
- MEDIA-007: a clip over 15 s or of unreadable duration is refused before any conversion runs.
- MEDIA-006 / MEDIA-008: an output still over 6 MB, or a failed conversion, attaches nothing and leaves no partial file.
- MEDIA-003: the output keeps no metadata but orientation (no location, device, capture time) — a device test parses the MP4 boxes.
- The release APK grows by at most 2 MB (measured and recorded); the release smoke test passes under R8.

**Notes:** Review round 1 found HDR sources could come out as 10-bit HEVC (Media3 keeps HDR by default and overrides the H.264 request); fix round 1 tone-maps to SDR through OpenGL (a unit test checks the composition; no HDR source can be made on the API 29 emulator), scales the bitrate with the pixel count (200 kbit/s – 2 Mbit/s), declares media3-effect/container, and the release script checks both smoke tests ran. Device: a 1920×1080 12 s 29 MB clip with sound and a location became 720×1280, H.264 only, 3.9 MB, no metadata but orientation. The release smoke test caught an R8 class merge that crashed on API 29 (an API 31 field); one narrow keep rule fixes it. Media3 1.11.1 adds about +1 MB once the converter is reachable (T-116). Merged on that evidence.

### T-117 — The clip plays on the card
**Status:** done
**Serves:** scenarios 1, 3, 4 · **Core:** no · **Depends on:** T-114
**Expected files:** `card/StepsList.kt`, new `card/StepVideo.kt`, `card/Cover.kt`, `strings_card.xml` (both); tests under `.../card/`.
**Criteria:**
- MEDIA-004 (3): a step's clip plays muted and loops while visible, pauses off screen; no control offers sound; a 56 dp play/pause control (A11Y-007, WCAG 2.2.2); it does not start by itself when the system's animations are off.
- A11Y-001: announced as the author's video.
- FLOW-061: a step or cover whose file is missing says its media is unavailable (not that it needs a connection) instead of silently showing nothing.
- Playback through the player T-115 brings in, or the platform player if T-115 is not merged yet — behind a small interface so the JVM tests use a fake.

**Notes:** Review round 1 found every clip step held a MediaPlayer and decoder from composition (the card is a scrolling Column), so many clips could exhaust codecs and latch "unavailable". Fix round 1 makes a player only while any part of the clip is on screen and releases it when it leaves, retries a failed clip when it returns, keeps the pause wish, draws the first frame when the surface comes late, and opens the file off the main thread; a fresh re-review passed and confirmed by mutation that the 8-clip test fails without it. Platform MediaPlayer, no new dependency. Nits left: a stopped (Home) card keeps its paused player; not yet checked on a real device.

### T-118 — Clear saved media after a warning
**Status:** done
**Serves:** scenario 5 · **Core:** no · **Depends on:** —
**Expected files:** `book/BookDatabase.kt` (a query), `recipe/RecipeRepository.kt`, `library/LibraryScreen.kt` (the book's ⋮ menu item and its dialog), `strings_library.xml` (both); tests under `.../library/`, `.../recipe/`.
**Criteria:**
- FLOW-060 (2): the action deletes the media files of every favourite (found recipe) and of every sent own recipe, never of an own recipe that was never sent; the rows stay, so FLOW-061 can say the media is unavailable.
- FLOW-060 (4): in serverless it first says the deleted media cannot be fetched again, and deletes nothing until the person confirms; Cancel changes nothing.
- When there is nothing to clear, the action says so instead of asking.

**Notes:** Passed review on the first round; the never-sent rule was checked by mutation (all seven tests failed). Data safety: a media row owns one file, an own fork copies its files under new ids and a found recipe's fork carries none, so clearing never deletes a draft's file. Nits left: the serverless warning names found recipes only, though a `SENT` own recipe would also be cleared — nothing in a serverless build sets `SENT`, so it matters only if a serverless build ever runs on a book a standard build sent from; the action clears the active book only (the one-database-per-book ADR), where FLOW-060 says "the device"; list covers may stay visible from memory until the process restarts.
