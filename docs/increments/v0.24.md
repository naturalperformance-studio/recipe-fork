## Goal
A step can hold more than one timer, and a GIF or animated WebP attached to a step plays like a clip.

## Demo scenarios
1. In the editor, a step offers "Add timer" more than once; each timer has its own name and duration; they can be removed one by one.
2. On the card, each timer of a step starts, runs and rings on its own, with its own notification; the running-timers bar lists them all; a recipe file keeps them.
3. Attaching a GIF or an animated WebP to a step turns it into a silent clip that plays on the card like any clip; a still image stays a photo.

## Out of scope
- Timers outside steps; a timer that depends on another.
- Animated covers.

### T-177 — An animated image becomes a silent clip (spike and converter)
**Status:** done
**Serves:** 3 · **Core:** no · **Depends on:** —
**Expected files:** new files in `app/media/` (an animated-image detector, duration reader and converter implementing `ClipConverter`), `AppContainer.kt` (wiring only), an androidTest beside `VideoConversionTest`, unit tests.
**Criteria:**
- A GIF or animated WebP is detected as animated (a still GIF/WebP/PNG/JPEG is not); its duration is the sum of its frame delays.
- It converts to an MP4 within the clip limits (≤ 15 s, ≤ 6 MB, ≤ 1280 px longer edge, no audio track) that the existing card player plays — proven on the emulator (`scripts/device-test.sh`) with a GIF and an animated WebP fixture; an animation over 15 s is refused as too long like a clip.
- No new library, or the lead approves one (APK growth ≤ 1 MB). If no route fits the limits, the task reports that and stops — the feature is then dropped and said so.
**Notes:** Route: own GIF/WebP parser → frames composed with disposal/blend → CPU BT.709 YUV → platform MediaCodec AVC → the app's MP4 muxer; no new library. Review 1: fix — a file declaring a huge canvas crashed the app (OutOfMemoryError, reproduced on the emulator), and files were read whole with no cap; folded in: frame rate from the frames, buffer reuse, one parse per add, a device test for hostile input. Review 2 (5 mutations caught; ~80k hostile and mutated files on the JVM, no crash or hang; 7/7 animation device tests): pass; merged 2026-10-09.

- 2026-10-09 `assumed` An unnamed timer is told apart from its step's other timers by its number in the step ("Step 3 · timer 2"); a step with one timer reads as today.
- 2026-10-09 `assumed` Several timers are a new `recipe.json` version (3), a book-database migration (4→5) and a timer-database migration (2→3); older files and running timers carry over.
- 2026-10-09 `assumed` An unnamed timer gets a number only when its step has more than one timer — its place among the step's timers; named timers get none, even when two share a name.
- 2026-10-09 `assumed` In a converted animation, a frame delay of 10 ms or less counts as 100 ms (as browsers do), transparent areas show on white, and an animated file holding one frame stays a photo.
- 2026-10-09 `assumed` On the card, in the notification and in the restart question, an unnamed timer of a multi-timer step reads "<its derived name> · timer N"; in the bar "Step N · timer K". A step's timers stack one per row, 8 dp apart. A running timer keeps the number it started with for its notification.
- 2026-10-09 `assumed` Animated images are capped: a canvas of at most 3840×2160 pixels, a file of at most 32 MiB, frames read only until 15 s; a frame reaching outside its canvas makes the file "not an animation" (it stays a photo). Anything that cannot be read or would not fit is refused like an unreadable clip, never a crash.
- 2026-10-09 `assumed` The sixth-timer statement: "A step can hold up to five timers. For more waits, split this step into further steps, each with its own timers." A timer row still without a duration counts toward the five. Removing a timer — a step's only one too — says "Timer removed from step N · Undo". With several timers, each one's labels carry its number ("Timer 2's name").
- 2026-10-09 `assumed` A running timer is matched to its step's timer at the same place; if that timer's duration or name changed — including because an earlier timer of the step was removed — the run ends rather than passing to another timer.
- 2026-10-09 `assumed` A step's only timer, while it holds no duration, now has a remove control too, and a timer row added by "Add timer" takes the focus in its hours field.
- 2026-10-09 `assumed` A step's animated image is checked off the main thread without a progress mark (the clip's "converting" shows once conversion starts); a file that fails the animation checks goes to the crop as a still photo.
