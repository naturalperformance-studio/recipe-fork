# v0.34 — The whole book saved to a file and restored
**Status:** active
**Planned:** 2026-10-12 · **Shipped:** —

Chosen by the owner on 2026-10-12 after v0.33 shipped, over metric ↔ US units (H-003) and the Google Play preparation. Builds FLOW-073 (`spec/70-flows/70-serverless-mode.md`), which must exist before the first public release; OQ-041 answered by the owner at planning: a restore into a book that holds recipes asks whether to add to it or replace it. Format: `docs/architecture/decisions/20261012-a-book-file-holds-the-books-database.md`.

## Goal
A lost or reset phone no longer loses the book: the reader saves the whole book — every recipe with its photos and clips — to one file wherever they choose, and restores it on any phone exactly as it was.

## Demo scenarios
1. Settings → "Save the book to a file" → the system's picker offers a place (Files, Google Drive, …) and a name "Recipe book 2026-10-12.recipefork-book" → a progress bar with Cancel → "Book saved: 14 recipes".
2. On a phone with an empty book (or after clearing the app's data): Settings → "Restore from a file" → pick that file → progress → every recipe is back: own ones editable, found ones still marked found, a fork still names its parent, photos and clips play; My kitchen is back.
3. Restore into a book that already holds recipes → a dialog "Add to the book" / "Replace the book" / Cancel. Add → "Added 3 recipes; 11 were already in the book", nothing already there changed. Replace → a second confirmation naming what goes → the book is exactly the file's.
4. Send the saved file to yourself in Telegram, tap it → the app opens and offers the same restore.
5. A file that is not a saved book, a damaged one, or one from a newer app → "This file can't be restored: …" and nothing in the book changes; cancelling a restore midway changes nothing either.

## Out of scope
- Automatic or scheduled backups, cloud sync, Android Auto Backup.
- Done marks, the shopping list and settings in the file (they stay on the phone).
- Choosing single recipes to restore from a file.

### T-239 — The book file: writing it and opening it
**Status:** fix
**Serves:** 1, 2, 5 · **Core:** no · **Depends on:** —
**Expected files:** `app/…/backup/` (new: the manifest, the writer, the reader), small seams in `book/` and `kitchen/KitchenStore.kt`, tests in `app/src/test`.
**Criteria:**
- Writing: from the active book, a zip as the ADR lays out (`manifest.json`, `book.db`, `media/…`, `kitchen.json`) to a given output stream, reporting progress by bytes and stopping when cancelled; the database copy is consistent (a full WAL checkpoint inside a read transaction, then a copy) and the book stays usable meanwhile.
- Reading: from an input stream into a directory of the app's own, checking the manifest (present, a known format, a book schema not newer than the app's) before anything else, then opening `book.db` as a book database of its own through the same migrations as a book on the phone; each refusal is a distinct outcome (not a book file, damaged, from a newer app) the screen can word; the directory is removed when the caller closes what it opened, and on any failure.
- Tested: a book of own, found and forked recipes with photos and a clip round-trips — the opened copy holds the same recipes, states, parents and media bytes; a file with a book of the previous schema version opens migrated; a non-zip, a zip without a manifest, a truncated file and a newer format are each refused with their outcome; a cancelled write leaves nothing half-written for the caller.
**Notes:** Developer (8a8fea0, ~800 lines): `backup/BookFileWriter.kt` (built under the cache, copied to the stream only when whole), `backup/BookFileReader.kt` → `Opened(OpenedBookFile)` | `Refused(NOT_A_BOOK_FILE, DAMAGED, NEWER, CANNOT_READ)`; `BookDatabase.open(context, file)`, `KitchenStore.replace` + `KitchenJson`. The ADR's snapshot could not work as written (no checkpoint inside a transaction; no read-only transaction on API 29): the `.db` and `-wal` are copied together inside a non-writing transaction and the log folded into the copy — the ADR now says so. Developer's L2: the manifest first or not a book file; generous size caps; counts checked against the manifest; media stored uncompressed; stale unpack directories swept at each open; a cancel during the final copy still finishes it, so T-241 deletes the destination on cancel or failure. Review 1 (probes: no -wal copy fails 4, the refusal not cleaning up fails 3, the zip straight into the stream fails the cancel test; snapshot safety read through: BEGIN IMMEDIATE, only .db and -wal inside the transaction): fix — must: nothing pinned the manifest being judged before unpacking. Nits taken (data safety): a `book.db` without the SQLite header refused (a non-SQLite file opened as an empty book, so a Replace would empty the book); media listed inside the snapshot; a failed unpack directory refused, not thrown; a work directory per write; a full disk while opening is CANNOT_READ.

### T-240 — Restoring into the book: add or replace
**Status:** planned
**Serves:** 2, 3, 5 · **Core:** no · **Depends on:** T-239
**Expected files:** `recipe/RecipeRepository.kt` or `book/` (the copy into the active book), `app/…/backup/`, tests.
**Criteria:**
- Add: every recipe of the opened file the active book does not hold (by id) is copied with its media files, ingredients, steps, references, equipment, groups and state; recipes already there are untouched; the outcome counts added and already held. A fork whose parent is in neither stays a fork naming its parent as the card does today.
- Replace: the book ends up exactly the file's — every recipe of the book not in the file removed with its media, every recipe of the file copied.
- Both run in one transaction of the active book's database, media copied into place before and the replaced files deleted after it commits; a failure or cancel at any point leaves the book and its media exactly as they were.
- My kitchen: merged on Add, replaced on Replace.
- Tested: Add into an empty book, into a book sharing some recipes (counts, untouched rows), Replace; own stays editable, found stays found; media files present after and old ones gone after Replace; a failure injected midway leaves the book unchanged.

### T-245 — Ticks the owner's phone can feel
**Status:** done
**Serves:** the owner's old note (later.md, v0.22 demo: ticks not felt on their Samsung) · **Core:** no · **Depends on:** —
**Expected files:** `ui/Haptics.kt`, its tests.
**Criteria:**
- A tick (the serving count walked by one, a dragged row passing a place) plays a one-shot vibration of 50 ms at the default amplitude instead of the predefined `EFFECT_TICK`; a confirmation (a timer started, stopped or cancelled) plays a one-shot of 80 ms instead of `EFFECT_CLICK`. Both keep the touch usage and the existing rule for the system's touch-feedback switch.
- Tested: the effect each haptic plays (durations), the usage, the switch rule as before.
**Notes:** Measured on the owner's phone 2026-10-12 (Samsung SM-A175F, Android 15) over adb: every tick reached the vibrator service and played (`usage: TOUCH`, `Prebaked=TICK`, `finished`) but scaled `LOW` (touch feedback off, touch intensity 1 of 5). Played to the owner by hand: the predefined TICK, CLICK and HEAVY_CLICK were not felt even unscaled; one-shots of 30 and 50 ms were; at ~35% amplitude 30, 40 and 50 ms were all felt, 50 ms best (the owner). Developer (4e8c3cd): `Haptic.oneShotMillis()` replaces `effectId()`; HapticsTest 12. Review (probes: a 51 ms tick fails 5 tests, a 50 ms confirmation fails 2): pass; merged 2026-10-12; ui-conventions' Haptics row updated by the lead.
