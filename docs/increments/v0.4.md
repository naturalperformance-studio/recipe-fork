# v0.4 — A recipe passed to a friend as a file
**Status:** demo
**Planned:** 2026-10-02 · **Shipped:** —

Goal, scenarios and out-of-scope below were approved by the user on 2026-10-02.

## Goal
Send a recipe to a friend as a file and take in theirs: it lands in the recipe book as a found recipe you can cook from and fork, and the fork names it as its parent.

## What exists at the start
On `develop` @ 43ed7f3 (v0.3 shipped). The book's `recipe` table already carries `owner`, `parent`, `stated_author`, `stated_parent_title` and `stated_parent_nickname`; the `favourite` table backs the view of marked recipes (`library/LibraryScreen.kt`, `MarkedList`), which nothing fills yet. There is no `Mode`, no `recipefork.serverless` property and no `:core` `file` package; `scripts/artefact.sh` builds one APK. A fork is made on the card (`card/Forking.kt`, `core/recipe/Fork.kt`) and its card names the parent by title when the book holds it ("Forked from a recipe that is not in this recipe book" otherwise). No account exists on the device, so every recipe is in the pool. Binding: ADR `20260928-recipe-file-is-a-zip.md` (format, importer checks) and ADR `20260928-serverless-mode-is-a-build-flag.md` (the flag, `Mode`, two APKs).

## Demo scenarios
1. On a recipe in the book choose "Export" → the system share sheet opens with the file → send it, e.g. to yourself in Telegram.
2. Open the file on a phone that does not hold that recipe → it appears in the marked view as a found recipe; it opens as a card that scales and runs timers, has no Edit and has Fork; a stated author, if any, is marked "stated in the file, not verified".
3. Open the same file again → nothing is added and the app says the recipe is already in the book; open a damaged file or one that is not a recipe file → refused, with the reason.
4. Fork the found recipe → an editable copy without the description; its card reads "Forked from “…”" and opens the parent; remove the found recipe from the book → the fork names its parent by title as unavailable.
5. In the editor: text inputs are the same height as the unit select; above each ingredient a lightly tinted header strip with a centred handle icon — the whole strip drags the block, and the inputs below no longer shift.

## Out of scope
- Media in a file (nothing carries media yet).
- Accounts and nicknames: an export made with no account names no author.
- The server, and the rest of serverless mode's sweep (FLOW-062 (1) — removing server controls: there are none yet).
- The usual serving count and scroll restore (FLOW-017, FLOW-012); photos (FLOW-026).
- Accessibility and localisation sweeps.

## Tasks
Order: T-075 and T-078 start together; T-076 follows T-075; T-077 and T-079 follow T-076 and run together.

Standing note for every task: leaving the editor shows the card, and tests reach the book through `compose.backThroughTheCard()`. ### T-075 — Serverless build and exporting a recipe to a file
**Status:** done
**Serves:** scenario 1 · **Core:** yes · **Depends on:** —
**Expected files:** `app/build.gradle.kts` (the property → `BuildConfig.SERVERLESS`); `MainActivity.kt`, `AppContainer.kt` (the `Mode`); `core/src/main/kotlin/app/recipefork/core/file/*` (new: the versioned `recipe.json` document and its writer) and its tests; `app/src/main/kotlin/app/recipefork/app/file/*` (new: writing the ZIP, `FileProvider`); `AndroidManifest.xml`, `res/xml/` (file paths); `library/LibraryScreen.kt` (the Export control on an entry); `strings_file.xml` (new, both); `scripts/artefact.sh` (the second APK); tests under `app/src/test/kotlin/app/recipefork/app/file/` and `.../library/`.
**Criteria:**
- `-Precipefork.serverless=true` builds an app whose `MainActivity` passes `Mode.Serverless` to the composition root; without it, `Mode.Standard`; nothing else reads the property or the build constant (ADR serverless-mode-is-a-build-flag). Both builds share one application id, so the serverless APK installs over the standard one keeping the book.
- `scripts/artefact.sh` produces `recipe-fork-debug.apk` and `recipe-fork-serverless-debug.apk`.
- In `Serverless`, every recipe entry in the book offers Export; in `Standard`, no export control exists anywhere (FLOW-062 (8)).
- Export writes a ZIP with the product's extension `.recipefork` and MIME type `application/vnd.recipefork.recipe+zip`, holding `recipe.json` with `format_version` 1 and the recipe's identity, title, language, tags, serving count, ingredients (dictionary entry or free text, quantity, unit, divisibility), steps with their references and timers, and description; the identity of its direct parent with that parent's title where the book holds it; no author when no account is active (FLOW-063 (3, 5)).
- The file is handed to the system share/save sheet through a `FileProvider`; the product sends it nowhere itself (FLOW-063 (7)).
- Exporting changes nothing in the recipe: an editable recipe stays editable (FLOW-063 (1)).
- `recipe.json` round-trips in `:core`: a recipe written and read back equals the original (references, timers and divisibility included).
**Notes:** Review round 1 passed the mutation check on every criterion and found one `must`: the serverless composition root still built the HTTP client and started the dictionary sync, so the serverless APK called the server whenever the network returned (ADR serverless-mode-is-a-build-flag, FLOW-061 (2)). Fix round 1: no client and no sync in Serverless, with a test; the file format pinned by explicit name tables and a golden `recipe.json`; the export cache cleared before each export; the FileProvider's narrow path and read-only grant tested; a failed export says so. Re-review passed with mutations; merged. Nits left: nothing tests that the Application starts the standard sync; the golden document does not exercise every unit and language name (folded into T-076); the serverless manifest still declares INTERNET.

### T-076 — A recipe file is imported as a found recipe
**Status:** done
**Serves:** scenarios 2, 3 · **Core:** yes · **Depends on:** T-075
**Expected files:** `core/.../file/*` (reading and validating the document); `app/.../file/*` (the importer, the intent filter's activity path, the document picker); `AndroidManifest.xml` (the `ACTION_VIEW` filter on the MIME type and extension); `library/LibraryScreen.kt` (the marked view: found recipes, removing one, an import action); `card/CardScreen.kt` (a found recipe's card: no Edit, the stated author); `book/*` and `recipe/RecipeRepository.kt` if the found recipe needs storage; `strings_file.xml` (both); tests under `app/src/test/.../file/`, `.../library/`, `.../card/` and `core/src/test/...`.
**Criteria:**
- In `Serverless`, opening a `.recipefork` file (from another app, or by the import action in the marked view) adds the recipe to the active book as a found recipe: it is listed in the marked view, opens in full, scales, and its timers run (FLOW-064 (1)); in `Standard`, opening a file imports nothing.
- A found recipe's card has no edit control and has the fork control (FLOW-064 (2)).
- A stated author's nickname shows on the card and the entry marked as stated in the file and not verified; a file naming no author shows no author (FLOW-064 (3)).
- A file holding a recipe already in the book — imported before, or the person's own — adds nothing and says it is already in the book (FLOW-064 (4)).
- A file that is not a ZIP, has no `recipe.json`, does not parse, has `format_version` above 1, or fails the importer's checks of ADR recipe-file-is-a-zip (entry names, inflation caps, the document's rules DOM-012/016/017) is refused with the reason said, and nothing is added (FLOW-064 (5)); each case is a test.
- A found recipe can be removed from the book from its entry, and leaves it with its content (FLOW-064 (6)).
- (From T-075's re-review) Every name in the file format's tables — each unit, unit type, language, state and media kind — is pinned by a test, so a typo in a table cannot pass unnoticed.
**Notes:** Before review the lead had incomplete and off-grid rows accepted on import (an exported draft must import). Passed review with the mutation check and hostile-file probes (deep nesting, oversized and empty-entry archives, unsafe names, nested zips) on the first round; merged. Review nits taken into T-079; left: duplicate JSON keys are accepted (last wins).

### T-079 — The importer stops early on hostile files
**Status:** done
**Serves:** scenario 3 · **Core:** yes · **Depends on:** —
**Expected files:** `app/src/main/kotlin/app/recipefork/app/file/RecipeArchiveReader.kt`, `RecipeImport.kt`, `book/BookDatabase.kt` (the found-recipe guard's test only); tests under `app/src/test/kotlin/app/recipefork/app/file/`. Not `core/.../file/*` or `card/*` (T-077).
**Criteria:**
- A file with more entries than a recipe can need is refused at once, and reading stops as soon as the document and every media item it names have been read; the copy loop stops when the import is cancelled.
- One ignored entry larger than the archive cap that declares a small size is stopped at the cap.
- A file with two `recipe.json` entries, and a document with invalid UTF-8 inside otherwise valid JSON, are refused — each with a test that fails without its check.
- Two imports of one recipe racing each other add it once (a test calls the store twice directly).
- A `file://` URI pointing into the app's own data directory is refused.
- Media files and rows go to the book that was open when the import began, even if the book changes meanwhile.
**Notes:** From T-076's review. Passed review with the mutation check on the first round; merged. Accepted trade-off: the document pass still reads the whole archive (bounded by the 53-entry and byte caps) so a second `recipe.json` is seen. Nits left: the document pass's missing/doubled-media check is masked by the media pass in tests; check-then-open on `file://` leaves a symlink race (low risk); a hand-rezipped file with extra entries (e.g. `__MACOSX/`) is refused.

## Decision log
- 2026-10-02 `decided` v0.4 is recipe files between people — export, import as a found recipe, fork naming its parent — plus the two editor fixes from the v0.3 demo (the user).
- 2026-10-02 `decided` Files exist only in the serverless build, as `spec/` FLOW-062 has it; until there is a server, the hand-test build the user gets is the serverless APK, installed over the standard one with the book kept (F-1, the user).
- 2026-10-02 `assumed` The file's extension is `.recipefork` and its MIME type `application/vnd.recipefork.recipe+zip`; if the product is renamed (OQ-016), a later app accepts both.
- 2026-10-02 `assumed` In the serverless build an entry's actions move to their own line under the title, at its end: Export, then Delete where offered; the standard build's entry is unchanged.
- 2026-10-02 `assumed` Export reads "Export" / «Экспорт»; the share sheet's heading "Export “<title>”" / «Экспорт «<title>»»; the file is named after the title (characters file systems refuse removed, cut to 80) with `.recipefork`, `recipe.recipefork` when untitled.
- 2026-10-02 `assumed` The ingredient's header strip is tinted with the theme's raised-surface colour, at least 48 dp tall, the existing handle icon at its centre; the unit select is drawn like an outlined text field, and the three inputs are evened to the tallest.
- 2026-10-02 `assumed` At 2.0 font scale, when "Количество" cannot fit on one line beside the unit, quantity and unit each take a full-width line; side by side otherwise.
- 2026-10-02 `assumed` The serverless build never refreshes the dictionaries: it keeps the snapshot shipped in the APK, since it calls no server.
- 2026-10-02 `assumed` A failed export says "Couldn't export the recipe" / «Не удалось экспортировать рецепт».
- 2026-10-02 `assumed` A found recipe is held as recipe rows plus a `favourite` row (no schema change), in state `link_shared` so it is not editable, owner none, never sent; the own view leaves marked recipes out.
- 2026-10-02 `assumed` An imported draft's incomplete or off-grid ingredient rows are kept as written and shown unscaled, as an own draft's are; only structurally invalid documents are refused — departs from ADR recipe-file-is-a-zip's "the same rules a sending must pass", because FLOW-063 exports drafts too.
- 2026-10-02 `assumed` Five refusal reasons, each said in a long toast: cannot open, not a recipe file, made by a newer version, damaged, breaks the recipe's rules; "already in the book" names the recipe by the title the book holds.
- 2026-10-02 `assumed` After an import the app shows the marked view; an Import button tops the marked view in the serverless build, and the picker accepts any file type; with nothing marked the view says "No recipes are marked in this book yet."
- 2026-10-02 `assumed` A found entry and its card read "Author: X (stated in the file, not verified)"; Remove sits on the entry, asks first, deletes the content with its media and cancels its timers.
- 2026-10-02 `assumed` The manifest's file filter is the same in both builds; in the standard build opening a file starts the app and imports nothing.
- 2026-10-02 `assumed` A fork is someone else's when the book marks its parent as found; such a fork stores the parent's title and stated author (no new column) and carries no description and no media; own forks are unchanged.
- 2026-10-02 `assumed` A fork of a found recipe reads "Forked from “Bean soup” (author: anna, stated in the file, not verified)"; once the parent is gone, "…, which is not in this recipe book"; a stated parent is always named by the title its file states, in the card and in an export.
- 2026-10-02 `assumed` A found entry in the serverless build carries Export and Remove on a line under its text, as own entries do.
- 2026-10-02 `assumed` A `file://` link into the app's own data is refused as "cannot open"; too many entries, two documents or invalid UTF-8 are refused as damaged.
