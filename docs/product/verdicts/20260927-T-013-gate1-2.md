**Stopped by:** Step 3 — the specification is silent on something the task cannot be built without (SD-013, omission).
FLOW-002 (1): "Given no network connection, when the owner creates a recipe and fills its title, servings, ingredients and steps, then every change is kept and is present after the application is closed and reopened." With FLOW-024 (1) moved to wave 5, this is the only wave-1 criterion that obliges the editor to take an authored serving count, so T-013 builds that field. What the field accepts is stated nowhere: the domain model types `servings` as "number", the glossary defines it only as the count the author wrote the quantities for, DOM-006 requires its presence and DOM-012 sets no limit. Whole or fractional, below one or not, zero or not (SCALE-001 divides by it), a ceiling or not — each is visible on the editor, and an authored count outside the set SCALE-011 lets a reader request cannot be requested back (FLOW-017, "returns it to the authored count"). The requested count's form was decided explicitly (SCALE-010, SCALE-011); the authored count's was not. Whoever builds the field would decide it, and gate 2 could not tell a right field from a wrong one. The gate does not choose a reading. Route: the user runs `/req-forge` on SD-013.

The reading under which the task would be accepted — `servings` is "number", so any number is admissible — does not hold without deciding the product: it admits 0, for which SCALE-001 is not computable, and values the card cannot display or return to as themselves; choosing it, or choosing the requested count's set, is the product decision SD-013 names.
