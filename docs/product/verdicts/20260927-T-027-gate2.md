**Failed check:** gate-2 sweep. The spec does not say whether the diff keeps a live requirement met.
The diff adds a stored table, `account_session (digest, account_id)`, in
`server/src/main/resources/db/migration/V3__recipes.sql`. The server writes one row
each time a device signs in with the account key (`POST /api/v1/sessions`,
`server/src/main/kotlin/app/recipefork/server/auth/Sessions.kt`). A row is the SHA-256
of a token that the device then presents with every request. Rows are never removed in
this diff. So the store now holds one record for each device that has held the account
signed in. The server can tell those records apart, and each one is bound to whatever
the device presents on every call.

AUTH-015 (2) reads: "Given the stored data of any account, when it is enumerated, then
it holds nothing that identifies a device (CON-001)". Its statement reads: "shall store
no device identifier of any kind". `spec/` does not define "identifies a device" and
reads two ways here:
- *It is a device identifier.* `spec/100-moderation.md:132` gives the cost of having no
  push channel: "a delivery token is a per-device identifier held by a third party and
  CON-001 keeps it out". `spec/45-auth/00-index.md:38-39`: "The product never learns a
  device identifier". A token that one device holds and presents on every request is,
  in that vocabulary, a per-device identifier. The product now holds it, as a digest.
- *It is not a device identifier.* The token is 256 random bits minted by the server. It
  derives from nothing the device is or announces. A new sign-in on the same device gets
  a new one. It identifies a sign-in, not a device.

The spec also leans toward a record of this kind. QUAL-009 counts every presentation of
an account key against ten a day per source. That makes "send the key with every
request" unworkable. AUTH-021 (3) needs every device holding the account to be "signed
out" when it next reaches the server. The binding ADR
`docs/architecture/decisions/20260927-keys-are-hashed-random-secrets.md` draws the
session from these two requirements. Under the first reading, those requirements and
AUTH-015 (2) meet here and disagree. Under the second, they do not meet at all.

Gate 2 cannot tell which reading was built, because the diff changed the test that
would tell. Class: ambiguity, and inconsistency under the first reading. This is not
`rejected`: under the second reading the diff keeps AUTH-015 (2), and a corrected diff
would face the same question. Choosing the reading is the product decision (TEAM-008),
so it was not chosen here.
