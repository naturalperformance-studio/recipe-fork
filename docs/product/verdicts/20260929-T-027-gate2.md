**Failed check:** gate-2 sweep. The spec answers one reachable case two ways, and the diff builds one of the two.
The diff adds a behaviour that no criterion asks for. A sending whose content is exactly the content the server now holds is answered `forked = false`. Nothing is written and no fork is made, whatever revision the sending names (`RecipeStore.send`, the line `if (current.content == content) return@transaction SendResult.Stored(current)`, which runs before the revision is compared). `DivergenceTest` "FLOW-008 (5) - device B's version that is the one the server already holds creates no fork and writes nothing" asserts it. In that test, B's version is made from revision 1 while the server holds revision 2. Its comment calls it "its earlier answer never arrived". That case is outside FLOW-008 (5)'s Given ("device B's version was made from the one the server holds"), so the test is not evidence for (5). It is a behaviour of its own. `DivergenceTest` "FLOW-008 (2) - device B sending the same version again gets the same fork, not a second one" is another case of the same kind.

A user can reach it. Examples: a mobile sending that the server commits but whose answer is lost, followed by the owner pressing send again (FLOW-005 still marks the recipe as holding unsent changes); or two devices making the same edit. The owner then either sees a fork of their own recipe, with T-038's notice, or sees nothing.

What `spec/` says, read and not chosen:
- FLOW-008's statement (`spec/70-flows/10-offline-and-sync.md:332-336`) makes the condition "the server's version has changed since the version the device's copy was made from". Criterion (5) (line 352) glosses no divergence as "made from the one the server holds". By these words the resend is a divergence, and the version sent becomes a `private` fork. The manual-sending ADR says the same ("if the server's revision differs … stores the sent one as a `private` fork").
- The same requirement also calls what is forked "the divergent local version" (line 335) and "a divergent version" (criterion 4, line 350). Its title is "Two devices that diverge", and its Source says "No edit is discarded" (line 372). By these words, a version that is the same as the server's has not diverged, and forking it keeps nothing that would otherwise be lost.
- FLOW-059 (8) (line 133) says that for "a server that does not answer … nothing of it reaches the server". A server that stored the sending and whose answer was then lost has had the sending reach it. The device cannot tell that server from one that never received it. So the case exists, although (8) says it cannot, and no requirement says what the owner sees when they send again.

Under the first reading, the diff fails the sweep. Under the second, it conforms. A corrected diff would face the same question in either direction. That is why the verdict is not `rejected`: rejecting would choose the first reading, and choosing it is the product decision (TEAM-008). Class: ambiguity (FLOW-008), and not implementable (FLOW-059 (8)). The reading under which the diff would be `accepted` is the second one. It does not hold on its own, because criterion (5) and the statement's condition point the other way.
