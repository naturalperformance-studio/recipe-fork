**Failed check:** C5. A carried criterion's *Then* cannot be gated as worded for part of its *Given*.
FLOW-059 (9) reads: "Given a sending the server stored whose answer did not reach the device,
when the recipe is shown, then FLOW-005 still marks it as holding changes not sent, and sending
it again is answered by FLOW-066" (`spec/70-flows/10-offline-and-sync.md:138-140`). FLOW-059's
statement counts a recipe's first sending as a sending (line 109). Before that sending the
recipe is marked "never sent and held on this device alone" (FLOW-005, line 258; (2), line 266).
`spec/` treats that as a different case from "holding changes not sent": FLOW-005's statement
lists the two apart, FLOW-006's statement says "was never sent or holds changes not sent" (line
291), and this gate read them so at T-028 (`20260929-T-028-gate1.md`, unknown (2)).
On a first sending, then, the criterion can be read three ways:
- Read to the letter, it requires the third mark. The device cannot tell this case from a
  sending that truly failed (FLOW-066 Source). It would then mark as sent a recipe that FLOW-005
  (2) says is held on this device alone.
- Read by "still" and the ADR's "keeps its mark", it requires the mark to stay "never sent".
  That is not the mark the criterion names.
- Read as reaching only a recipe already sent, it leaves the first sending with no criterion
  at all.

The class is ambiguity. Under the first reading the criterion is also not implementable.
The counterfactual is the reading under which the entry passes. "Still" governs, so the mark is
unchanged, and "never sent" counts as "holding changes not sent" in a loose sense. It does not
hold, for two reasons. It needs the two cases that `spec/` keeps apart to be merged. And gate 2
could mark a first-sending test met only by choosing that reading, which is the product decision
(TEAM-008).
Rejecting the task would not help. C5 obliges it to copy these words, so it would come back
unchanged and spend one of its two returns on a defect that is not its own (TL-011).
