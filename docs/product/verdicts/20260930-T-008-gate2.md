**Failed check:** gate-2 sweep — observable behaviour that no criterion of this entry asks for, and that contradicts a live requirement.
In the diff, every entry of the own-recipes view becomes a way into the editor. In `LibraryScreen.kt`, `OwnEntry` gains `.clickable(onClickLabel = stringResource(R.string.library_own_open_action), onClick = open)`, and `open` is `session.openEditor(row.recipeId)`. `LibraryScreen` then composes `EditorScreen` for that recipe. The screen reader announces the entry as "Open the recipe" / «Открыть рецепт». This holds for a recipe in every state. A recipe in `pending`, `link_shared`, `published`, `reported_hidden` or `removed` opens in the editor with the statement "This recipe cannot be changed in its current state." (`editor_frozen`), as the tests themselves drive it: `EditorScreenTest.notEditable`, `EditorLanguageAndAccessibilityTest.everyScreen` ("The editor on a recipe that cannot be changed", opened from `LibraryTags.entry`).
- None of this entry's eleven criteria asks for opening an existing recipe from its entry. FLOW-042 (4) opens the editor on a *new* recipe from the empty view's offer. FLOW-024 (6) is evidenced without the entry route by `EditorSessionTest` (leaving by the home action, and the process ending, then returning to the editor).
- FLOW-029 (`spec/70-flows/40-editor.md`, carried by T-018) states what opening a saved own recipe shows. Criterion (1): "Given a recipe the author saves, when it is opened afterwards, then it is the same card a reader sees (FLOW-019, FLOW-020), not an editor with reader styling." Criterion (4): "Given a recipe that is no longer editable by `entity-states`, when the author opens it, then the card screen's bar carries no edit action and no way into the editor is offered at all." The ADR `spec/decisions/20260927-the-editor-is-entered-from-the-cards-bar.md` places the way into the editor in the card screen's bar. The entry route contradicts (4) outright for the five frozen states. It also puts an editor where (1) puts the card.

Counterfactual: this would pass if some criterion this task carries required reaching an existing recipe's editor from its entry. FLOW-002 (4) is the only candidate: "when its owner opens it, then it is not editable". It does not name the editor as what opens, and FLOW-029 (4) says what opening a frozen recipe shows. Gate 1 accepted a seeded recipe as evidence of what the editor allows (`20260929-T-008-gate1.md`, unknown (5)). That is a test fixture and not a route a user can take. `EditorScreenTest.theEditorRefusesAChangeToAFrozenRecipe` observes the editor's refusal without the route.

Consequence, stated once: several tests reach an existing recipe through the entry route. These are `EditorScreenTest.openOwn` (FLOW-002 (3), (4)), `leaveAndReturn` (FLOW-024 (6) by Back), `offlineTheTagEditorOffersExactlyWhatItOffersOnline` (FLOW-001 (1)), and the last two sections of `EditorLanguageAndAccessibilityTest.everyScreen`. With the route gone, the evidence for those criteria has to come from what remains. The next gate 2 re-walks all of them. The entry records 2 of 2 returns with the user's third run spent, so this rejection goes to the user (TL-011).
