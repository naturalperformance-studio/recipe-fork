**Failed check:** C3 — the behaviour the task describes is narrower than the criterion it carries. The Given is also left open where the task's own rule meets a module it does not scan.

L10N-001 (2), carried here word for word: "Given a release, when its interface strings are enumerated, then none is fixed in the code in one language only." Its Given is the release. The entry fixes the enumeration at "every Kotlin and Java source the app module compiles". The release is wider than that:

- The app module depends on `:core` (`app/build.gradle.kts:65`, `implementation(project(":core"))`), so `:core`'s code ships in the release.
- `:core` holds interface strings in its code. `core/src/main/kotlin/app/recipefork/core/scaling/QuantityText.kt:20–33` (`UnitLabels`) names the twelve units of DOM-016 in Russian and in English. DOM-016 (1) requires those units to be "named in the interface language". The file's own comment ties them to L10N-001 and L10N-009. No screen on `develop` or on `task/T-008` shows them yet. They are the release's interface strings all the same, and the cooking card of T-018 and the unit field of T-011 are built on them.
- `:core` is also where T-031 (`core/.../text/**`) and T-011 (`core/.../recipe/**`) add code. Both depend on T-043, and both carry L10N-001 (2) "through these checks".

As sliced, a one-language literal added to `:core`'s code passes the only check this backlog builds for L10N-001 (2). A test built to the entry therefore cannot be evidence at gate 2 for "a release". It would report a conformance over the app module, and for the rest of the release none would be measured. This is the failure the entry was cut to remove, where a check does not bite.

Widening the scan is not a mechanical fix either. Read as written, the rule is that "a string literal holding a letter fails unless its exact value is on a short allow-list … (test tags, log tags, SQL, route and key names)". Applied to `:core`, it fails `UnitLabels`. Those labels are held in both languages, so they meet L10N-001 (2) as worded. Failing them is wider than the criterion, and the allow-list categories the entry names do not cover them. The task's title, "Interface text comes only from resources", states that stricter rule. The criterion does not state it: it forbids text fixed in the code "in one language only". So the entry is narrower than the criterion if `:core` is left out, and wider than it if `:core` is scanned under this rule. Which way it is sliced is the Team Lead's decision. Either way the entry has to say how the release's interface strings outside the app module are enumerated.

Counterfactual: the entry would pass C3 if "the release's interface strings" could be read as those the app module holds. That reading does not hold. DOM-016 (1) makes the unit names interface text, and the release's unit names live in `:core`. A11Y-003 (1) is not a ground of this verdict. Its Given ("any screen") is met by the library (on `develop`) and the editor (on `task/T-008`), which are the only screens that exist. The gate found nothing in its reading that fails. Its unknowns (b), (2) and (3) are recorded for the re-gate.
